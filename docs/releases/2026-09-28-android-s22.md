# Android physical-device test: Galaxy S22 Ultra

Test date: 2026-09-28 JST. The device was connected to `jx` by USB and controlled
through its authorized ADB server over the existing SSH tunnel. Each command
selected the physical device explicitly.

## Device and builds

- Samsung Galaxy S22 Ultra, model `SM-S9080`.
- Android 16 / API 36; security patch 2026-08-05.
- Display: 1080 x 2316, density 450.
- Release: `jp.jacky.kana`, version `1.0.0 (1)`, source `da91138`.
- Release APK: `build/android-internal-20260928/kana-1.0.0-1-final.apk`, generated
  from the exact bundle uploaded to the internal track.
- Installation for these checks: ADB, with the upload signature. The installed
  APK's SHA-256 matched the archive:

```text
dec29441a334eca029f5562829a73af21a7f382fc090ac93681ee613b5b7df3f
```

Kana was not installed before this session. Debug and instrumentation packages
were installed for the existing test suite, then removed before the release
checks. Test data created in this session does not contain user practice history.

## Automated checks

The existing instrumented suite passed **9 of 9 tests** in 7.952 seconds on the
S22. It covers practice, answer highlighting, menu actions, the kana chart,
localization, and coffee UI. These tests use fakes for billing, ads, sound, and
sharing. The following additional checks drove the actual release app with ADB
and UI Automator.

| Check | Observed result |
| --- | --- |
| Cold start | Passed; first measured activity launch was 339 ms |
| Correct answers | Four consecutive correct answers increased the count and best streak |
| Wrong answer | Count increased; the question stayed visible and the correct answer was highlighted |
| Background timer | After 8 seconds on the home screen, the question retained its remaining answer time |
| Menu timer | An 8-second menu pause did not consume the remaining answer time |
| Process restart | Answer count and best streak persisted |
| Rotation | Portrait and landscape retained the question and choices; all four answers remained visible |
| System appearance | Practice and chart text remained readable with system dark mode; portrait and landscape also passed with system light mode |
| Kana chart | Hiragana and katakana tabs worked; scrolling reached the final katakana row |
| Offline practice | With Wi-Fi and mobile data off, cold start, saved statistics, and a new answer all worked |
| Sharing | Native share chooser opened with the app text and correct Play URL; it was dismissed without sending |
| Release stability | App process log and package exit history showed no app crash or ANR during the recorded checks |

Screenshots were inspected for portrait, landscape, wrong-answer feedback, and
chart readability. Audible sound output and physical tablet behavior still need
separate checks.

## Google Play Billing

The device's Play account matches the configured internal tester and license
tester. The test invitation was accepted on the device. The real billing service
returned the Japanese price of JPY 300. Before purchase, Restore correctly
reported that the account had no previous purchase.

The first purchase attempt returned `ITEM_UNAVAILABLE` (code 4), and the Play
installation page showed `Item not found`. A later purchase attempt opened the
test payment sheet. Every submitted payment used a Play test card and displayed
the no-charge test-order notice.

- Cancellation returned to the coffee sheet with the purchase action available.
- The always-decline test card produced Play's rejection and the app's purchase
  error. The purchase action became available again.
- The slow-approve test card showed `Awaiting approval` without the purchased
  confirmation. Play then approved the order, and the app changed to
  `Supported · Ads removed` without another purchase action.
- The purchased state survived an offline cold start. The new app process made
  no UMP request during that check.
- After app data was cleared, practice statistics were zero and Play restored
  the purchase automatically at launch. Another online process restart retained
  the restored purchase.

The installation page still showed `Item not found` at the final store check,
after test purchases had started working. Installation through Play remains
unverified; the device runs the ADB-installed release APK. Initial propagation
is a possible cause, not a confirmed diagnosis. Google's
[testing guide](https://support.google.com/googleplay/android-developer/answer/9845334?hl=en)
notes that the first test link can take several hours to become available.

## Ads and consent

The device could not reach the UMP endpoint. App logs recorded a connection
failure for `fundingchoicesmessages.google.com` at IPv6 `[::]:443`. A separate
device lookup resolved that same hostname to `127.0.0.1`. This blocks the consent
request on the current device or network path; it does not establish an app code
failure. No network filtering settings were changed.

UMP and banner delivery remain unverified on this device. Repeat them on a
registered test device where the consent endpoint is reachable. Do not click
production ads.

## Final device state

Wi-Fi, mobile data, rotation settings, and system night mode match the initial
values. The debug test package was removed. Release `1.0.0 (1)` remains installed
and open on the practice screen, with the Play test purchase restored. Practice
statistics are zero after the restore check cleared this session's test data.
The existing ADB tunnel remains running.
